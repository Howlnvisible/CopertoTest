# Coperto — стоп-лист кухни

Тестовое задание Middle Frontend Developer: один экран управления доступностью позиций меню. Фильтр меню по цеху и статусу, позиционированние  в стоп-лист, редактирование причины и срока или возврат позиции в продажу.

## Запуск

Для установки и запуска всех инструментов проекта используется Node.js 24.x и npm. Переменные окружения и внешние сервисы не требуются.

Локальны запуск:

```bash
npm install
npm run dev
```

Приложение доступно на [http://localhost:3000].

Запуск production сборки:

```bash
npm run build
npm run start
```

## Реализация

- 15 позиций из сида: название, цех, остаток, статус, причина и срок стопа.
- Фильтры в URL. Сохраняются после перезагрузки и работают с навигацией назад/вперёд.
- Панель постановки и редактирования стопа с проверкой полей при потере фокуса и отправке формы.
- Оптимистичное изменение строки, отметка «Сохраняется…», откат при ошибке и уведомление.
- Состояния загрузки, ошибки с повторной загрузкой и пустой выборки.
- Управление панелью с клавиатуры: Esc, начальный фокус, фокус ошибки и возврат фокуса после закрытия.

Вёрстка рассчитана на десктоп 1280 px. На узком экране таблица прокручивается внутри контейнера, панель ограничена шириной экрана.

## Стек

Next.js App Router, React, TypeScript в strict режиме, Tailwind CSS, TanStack Query, Zustand, React Hook Form и Zod. Проверки: ESLint, Prettier, Vitest и React Testing Library с jsdom. Сборка приложения выполняется Next.js/Turbopack; Vite используется для запуска теста через Vitest.

## Структура и FSD

```text
app/
  layout.tsx                 Корневой layout и подключение провайдеров
  page.tsx                   Серверная оболочка экрана
  api/menu-items/            GET списка, POST stop и resume
src/
  _app/
    providers/               QueryClientProvider
    styles/                  Глобальные стили и цветовые токены
    api-routes/              Реализация серверных обработчиков
    mock-api/                Сид и хранилище в памяти процесса
  _pages/stop-list/
    model/                   Разбор и изменение URLфильтров
    ui/                      Композиция экрана и состояния списка
  features/manage-stop/
    model/                   Форма, мутации, оптимистика и стор панели
    ui/                      Действия строки и панель управления
  entities/menu-item/
    model/                   Типы, константы и схемы валидации
    api/                     Запросы, query options и ключи кэша
    ui/                      Представление строки меню
  shared/
    api/                     HTTP клиент, контракты и ApiError
    ui/                      Кнопка, поле, диалог и тосты
```

Корневой `app/` содержит точки входа App Router, а FSD код находится в `src/`. Имена `_app` и `_pages` отделяют архитектурные слои от специальных каталогов маршрутизации Next.js (по рекоммендации спецификации Next.js + FSD). Alias `@/*` указывает на `src/*`; слайсы предоставляют публичные экспорты через `index.ts`. Строка сущности принимает действия через пропс и не импортирует фичу управления стопом.

### Граница сервера и клиента

`app/layout.tsx` и `app/page.tsx` серверные компоненты. Они задают документ, метаданные и оболочку страницы. Клиентский `QueryProvider` создаёт стабильный QueryClient; экран списка, фильтры и панель используют клиентские хуки. Область с `useSearchParams` обёрнута в Suspense. Меню загружается в браузере через GET; предварительной загрузки данных на сервере и гидратации кэша нет.

Route handler работают в runtime'е Node.js и обращаются к модулям с `server-only`. Сид и хранилище не входят в клиентский граф импортов. Общая Zod схема не зависит от серверного окружения и применяется как в форме, так и перед изменением данных в API.

### Архитектурные решения

TanStack Query хранит серверные данные, а Zustand только id открытой позиции и тосты, поэтому объекты меню не дублируются между хранилищами. Небольшой список загружается целиком и фильтруется по URL на клиенте, что позволяет менять фильтры без дополнительных запросов. Запросы и ключи кэша находятся в сущности, сценарии мутаций в модели фичи, поэтому UI не формирует HTTP запросы. При оптимистичном изменении сохраняется предыдущая версия одной позиции, её откат не отменяет успешные изменения соседних строк.

## Работа с данными

| Метод и маршрут                 | Поведение                                                  |
| ------------------------------- | ---------------------------------------------------------- |
| GET /api/menu-items             | Полный список, искусственная задержка 400 мс               |
| POST /api/menu-items/:id/stop   | Постановка или редактирование стопа; JSON с reason и until |
| POST /api/menu-items/:id/resume | Снятие со стопа, тело запроса не требуется                 |

POST обрабатываются с задержкой 600 мс и после проверки входных данных примерно в 20% случаев возвращают имитированную ошибку 500 до записи в хранилище. Это намеренное поведение для демонстрации отката. Успешный ответ содержит `{ data: ... }`, ошибка — `{ error: { code, message, fieldErrors? } }`. Ошибки валидации возвращают 400, отсутствующий id 404, снятие при нулевом остатке 409.

В `onMutate` отменяется текущий GET, сохраняется прежняя позиция и обновляется кэш. `onSuccess` записывает подтверждённую сервером позицию, `onError` откатывает только её и показывает уведомление. В `onSettled` после последней активной мутации выполняется инвалидация с GET для синхронизации списка. Новая мутация отменяет ещё выполняющийся GET через AbortSignal; повторное действие над тем же id блокируется.

Автоматические повторы запросов и обновления по фокусу окна отключены. Смена фильтра не выполняет GET. Фоновая загрузка сохраняет уже показанный список вместо повторного скелетона.

## Правила и ограничения

В форме используется местное время браузера; при отправке оно преобразуется в ISO. При остатке 0 возврат в продажу запрещён и в UI, и в API. Для уже остановленной позиции открывается форма редактирования.

Данные хранятся в Map на `globalThis` одного процесса Node.js. Перезагрузка страницы сохраняет изменения, перезапуск серверного процесса сбрасывает их к сиду.

Истечение конкретного срока и значение «до конца смены» пока не запускают автоматическое снятие со стопа. Возврат в продажу выполняется вручную. Поиск, сортировка, пагинация, авторизация и история изменений не входят в объём задания. Эти таски я бы вынес в отдельный "спринт" для реализации, как задачу по улучшению нашего приложения.

## Проверки

| Команда                | Назначение                                    |
| ---------------------- | --------------------------------------------- |
| `npm run lint`         | ESLint без предупреждений                     |
| `npm run typecheck`    | Генерация типов Next.js и проверка TypeScript |
| `npm run format:check` | Проверка форматирования                       |
| `npm run format`       | Форматирование файлов                         |
| `npm test`             | Регрессионный тест оптимистичных мутаций      |

Добавлен один тест: две параллельные мутации сразу меняют кэш, одна завершается успешно, другая откатывается без потери соседнего изменения. Тест также проверяет уведомление и финальную синхронизацию после размонтирования компонентов, запустивших запросы.

## Что улучшить при наличии времени

- Добавить серверную проверку истечения срока и автоматический возврат в продажу независимо от открытой страницы. При остатке 0 позиция должна оставаться в стоп-листе; для `until: null` нужно сначала определить момент завершения смены.
- Добавить тесты граничных значений срока и несколько сквозных сценариев для URL-фильтров, ошибок API и работы панели с клавиатуры.
- Проверить диалог и уведомления со скринридером и в других браузерах.
- придерживание подходу mobile-first, если бы в задание входила мобильная верстка
